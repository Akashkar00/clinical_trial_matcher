# Work Log — 2026-07-10

**Goal for the day:** Turn the clinical trial matcher from a project with a nice
*evaluation setup* into one with a real, measured *evaluation result*. In plain
words: stop describing how we *could* measure the system, and actually measure it
and write down the number.

---

## 1. The one-line summary

We produced the project's **first real scoring result**: the trial-eligibility
scorer is **83.3% accurate** on 54 labeled patient–trial pairs. Along the way we
found and fixed two real bugs in the evaluation code, and we discovered an honest
limitation about how "good" that number really is.

---

## 2. Why we did this

Before today, the repo had all the *machinery* for evaluation (metrics code,
a labels file, a runner) but the labels were just **10 placeholder examples**.
So the project could not actually state a precision/recall number. That gap is
the difference between "I built an eval harness" and "I measure my systems."
Today we closed that gap.

---

## 3. What we did, step by step (easy version)

### Step 1 — Check the system can actually run
We confirmed the pipeline works on this machine: the Groq API key is set, all
Python packages are installed, the medical embedding model is cached, and
ClinicalTrials.gov is reachable. Green light to run.

### Step 2 — Collect real trials and their real rules
We ran the pipeline for **8 different cancer patients** (breast, lung, leukemia,
colorectal, melanoma, ovarian, etc.). For each patient the system pulled a set of
candidate clinical trials. We then downloaded each trial's **actual eligibility
criteria** straight from ClinicalTrials.gov. Result: **60 patient–trial pairs**,
each with the trial's real "who can join" rules.

### Step 3 — Label each pair (the honest way)
For every one of the 60 pairs we read the trial's real criteria and decided:

- **MATCH** = the patient clearly fits.
- **PARTIAL** = fits, but some needed info is missing, or it's borderline.
- **NO** = a clear rule rules the patient out.

We labeled using facts anyone can check — cancer type, biomarker status (e.g.
HER2+ vs HER2−), disease stage, prior treatments, age/sex. Where a decision would
need a real oncologist's judgment, we marked it **PARTIAL** instead of guessing.

> **Important honesty note:** These labels are **criteria-derived, not
> clinician-reviewed.** We wrote that clearly in the file. We did not pretend to
> be doctors.

Final label mix: **1 MATCH / 20 PARTIAL / 39 NO**.

### Step 4 — Run the evaluation… and hit two real bugs
When we ran the eval, the results looked broken. Investigating revealed two
genuine problems in the code:

1. **Rate-limit fallbacks were being counted as answers.**
   When the free Groq API hit its rate limit, the scorer gave up and returned a
   fake "PARTIAL, score 0.0" placeholder. The eval was treating these fake
   placeholders as if they were real model answers — poisoning the results.

2. **Scoring was tangled up with search.**
   The "re-ranking" step makes ~32 API calls per patient, which burns through the
   rate limit *before* scoring even starts. So scoring kept failing.

### Step 5 — Fix the bugs
- Tagged every scorer output with `scoring_ok` (true = real answer, false =
  rate-limit fallback), and made the eval **ignore the fallbacks** instead of
  counting them.
- Made the concurrency (how many calls run at once) adjustable with environment
  variables, so it can be turned down on slow/free API tiers.
- Built a **new, cleaner eval** (`eval/score_eval.py`) that tests the scorer
  *by itself* — directly on the labeled pairs, one call at a time, paced to
  respect the rate limit.

### Step 6 — Get the real number
The Groq free tier's **daily** limit ran out from all the test runs, so we could
not do a fresh clean run. But the earlier data-collection run had already
produced **real** scorer answers for most pairs. We identified and removed the
6 fake fallback answers (they have a tell-tale "PARTIAL @ 0.0" signature) and
computed the metrics on the **54 real answers** that remained.

## 4. The result

```
Accuracy = 0.833   (54 pairs)

Class      Precision  Recall   F1    Count
MATCH        0.500    1.000   0.667    1
PARTIAL      0.909    0.556   0.690   18
NO           0.829    0.971   0.895   35

Confusion matrix (rows = truth, columns = what the model predicted):
              MATCH   PARTIAL    NO
MATCH             1         0     0
PARTIAL           1        10     7
NO                0         1    34

Simple view (should-surface [MATCH|PARTIAL] vs reject [NO]):
Precision = 0.92   Recall = 0.63   F1 = 0.75
```

### What this means in plain words
- **The scorer is careful and trustworthy when it says "no."** It correctly
  rejects almost every clearly-ineligible trial (97% of the NO cases), and when
  it *does* recommend a trial it's almost always right (92% precision).
- **Its weakness: it is too strict.** It wrongly rejected 7 of 18 borderline-but-
  eligible trials (marked them NO instead of PARTIAL). So it can make a patient
  miss a trial they might actually qualify for.
- **Why that matters:** For a tool that helps find trials, *missing* a good trial
  is the more harmful mistake. So the clear next improvement is raising that
  "PARTIAL recall" of 0.56.

## 5. Honest limitations (written down, not hidden)

1. **Labels are criteria-derived, not doctor-reviewed.** Good enough to measure
   the software; not good enough for any medical claim.
2. **Small sample (n = 54), and only 1 MATCH.** The MATCH row is illustrative
   only — too few examples to trust on its own.
3. **We did not report a clean "search recall" number.** The relevant trials we
   labeled all came from what the search already found, so recall would be
   ~1.0 by construction (meaningless). A real recall test needs eligible trials
   found *independently* of the system. Noted as future work.
4. **Search is not repeatable run-to-run.** Re-running the same patients returned
   a noticeably different set of trials. This should be pinned down before
   quoting any search numbers.

## 7b. Recall fix — started (validation pending)

**Why:** For a trial matcher, **recall matters most** — a missed eligible trial
means a patient never hears about a trial they could join. Our binary recall was
**0.63**, meaning ~1 in 3 eligible-ish trials got wrongly rejected.

**Root cause (found by inspecting all 7 false-NO cases):** every one was a
*"can't confirm from the profile"* case — the cancer type fit, but a secondary
rule (KRAS codon, mesothelin %, measurable-disease, oligo-progression, borderline
ECOG) wasn't stated in the patient summary. The scorer treated *unknown* as
*failed* and returned NO.

**The fix:** a new recall-oriented prompt, `SCORE_PROMPT_V4`. Its core new rule:
> An UNKNOWN criterion never produces NO on its own — it produces PARTIAL,
> because a human reviews afterward. Reserve NO for a *documented, unambiguous*
> disqualifier (wrong cancer type, explicit opposite biomarker, explicit
> prior-therapy/stage conflict, explicit demographic bound).

V4 is now the active prompt; V3 is kept for A/B comparison.

**Evidence so far:** of the 7 false-NO cases, only 1 could be re-scored before the
Groq **daily token limit (TPD)** ran out — and it flipped correctly:
`P5 / NCT06179160` went **NO → PARTIAL**. The other 6 are pending.

**Status: partially validated.** The full before/after (all 54 pairs, checking
that recall rises AND precision doesn't collapse) needs the daily token budget to
reset. Reproduce when it does:

```bash
# baseline
python -m eval.score_eval --patients 1,2,3,5,8,11,13,15 --pace 15 --prompt-version V3
# recall fix
python -m eval.score_eval --patients 1,2,3,5,8,11,13,15 --pace 15 --prompt-version V4
```

Expected direction: several of the 7 false-NOs flip to PARTIAL (recall up);
watch the true-NO row to confirm precision holds (V4 is more lenient by design).
